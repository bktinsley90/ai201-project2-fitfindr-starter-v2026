# Acceptance criteria — FitFindr

Five criteria that say what "working" means for this agent, written in unit 3
**before** any results existed.

An acceptance criterion names a target: a number, a count, a rate, or something
a person could plainly observe. *"The agent handles errors"* is an opinion.
*"When search returns nothing, the agent stops before calling the second tool,
in 5 of 5 tries"* is a criterion.

Under each one, write a sentence or two on **why that target** and not a
stricter one. A reason that says something about your tools, your loop, or the
data earns credit; *"80% seemed reasonable"* does not.

> Missing your own targets next unit costs you nothing. Setting a target so
> easy you can't miss it does.

**Two are written for you. You write three.**

---

## 1. A matching query completes all three tools

Given a query that matches at least one listing, the agent completes all three
tool calls and returns a fit card — in at least 4 of 5 tries.

**Why this target:**
I picked 4 of 5 because search is a plain keyword match, so some phrasings can miss even when a listing is relevant. Requiring every try to complete all three tools would also make an occasional model failure look like a search failure.

---

## 2. An impossible query stops before the second tool

Given a query that matches no listings, the agent stops before calling
`suggest_outfit` and returns a message naming what to change — 5 of 5 tries.

**Why this target:**
I picked 5 of 5 because the empty-results branch is deterministic loop logic and does not depend on the model generating a particular answer. For a query with no matches, calling `suggest_outfit` would be a bug every time, not an acceptable variation.

---

## 3. The selected item reaches the outfit tool unchanged

Across five matching-query runs, `session["selected_item"]["id"]` matches the `new_item["id"]` received by `suggest_outfit` in all 5 runs.

**Why this target:**
I picked 5 of 5 because passing the selected listing into the next tool is deterministic state handling, not model-generated content. Comparing IDs checks that it is the same listing without requiring unrelated dictionary details to be identical.


---

## 4. Fit cards contain the required details

For five different listings, at least 4 of 5 fit cards are 2-4 sentences and mention that listing's title, price, and platform. The wording may vary between cards.

**Why this target:**
I picked 4 of 5 because the fit card is generated by a model, so occasional wording variation or a missed detail is possible. I care that most cards contain the required information and are caption-length, not that they use identical wording.


---

## 5. The agent handles an unavailable model


If `suggest_outfit` or `create_fit_card` raises `ModelUnavailable`, the agent
returns the session with a non-empty `error` message explaining that the model
could not be reached, instead of printing a traceback — in 5 of 5 simulated
failures.


**Why this target:** I picked 5 of 5 because handling the known
`ModelUnavailable` exception is deterministic loop behavior, not model-written
content. The model service itself may be unreliable, but once the exception is
raised the agent should always return a usable error message rather than crash.
